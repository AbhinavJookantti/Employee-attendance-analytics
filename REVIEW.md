# REVIEW.md

I reviewed the starter `app/main.py`. Line numbers below point at the original starter, before my changes.

For rows 1 to 5 I ran the starter's own helper functions with the inputs shown and copied the numbers it gave. For the endpoint rows I read the code, compared it with `openapi.yaml`, and wrote down the input that triggers the problem.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes`, lines 36-37 | It cuts the time down to whole minutes first and only then checks `> 10`. So anything a few seconds past 10:00 is treated as on time. The contract says late means strictly more than 10:00, and then `late_minutes` is the full minutes since shift start. | Shift 09:30, punch-in 09:40:01. The starter returns 0, it should be 10. | Compare the whole seconds with 600 first, then divide by 60 and floor. |
| 2 | `compute_late_minutes`, line 35 | It builds the shift start on the punch-in's own calendar day. For an overnight shift, a punch-in after midnight belongs to the previous day's shift. | Shift 22:00, punch-in at 00:30 on the 7th (attendance date is the 6th). The starter returns 0, it should be 150. | The shift start is built from the record's attendance date, which I work out separately in `attendance_date_for`. |
| 3 | `compute_work_hours`, line 41 | `round()` on a float is not half-up. 2.675 is stored a tiny bit below the halfway mark, so it rounds down. | 9630 seconds gives 2.67 (should be 2.68). 450 seconds gives 0.12 (should be 0.13). | `Decimal` division with `ROUND_HALF_UP`. |
| 4 | `compute_overtime`, line 46 | The shift end is always put on the record date, so an overnight shift "ends" 24 hours too early. | Shift 22:00-06:00, punch-out 06:40 next morning. The starter says 1480, it should be 40. Punch-out at 23:00 says 1020, it should be 0. | I added an optional `shift_start` argument. If the shift end is not after the start, the end moves to the next day. |
| 5 | `compute_overtime`, line 47 | There is no 30 minute minimum. Any positive number of minutes counts. | Punch-out 29 minutes after shift end. The starter returns 29, it should be 0. | Return 0 when the minutes are below 30. |
| 6 | whole file, lines 22, 82, 102 | Time handling depends on the machine's time zone. `datetime.now()` and `fromtimestamp()` give naive local datetimes, and the Mongo client is not `tz_aware`. I only checked this by reading the code, I did not run it on a server in another zone. | Reading line 102: `fromtimestamp` uses the machine's zone, so the attendance date could differ on a server that is not in IST. | Everything is UTC-aware now. IST is used only when working out the date and shift times. The client uses `tz_aware=True`. |
| 7 | `punch_in`, line 102 | Fractions of a second are kept. R1 says to cut to whole seconds before anything else. | A `punched_at` ending in 900 ms is stored with the 0.9 s. | `from_millis` drops the microseconds before any calculation or storage. |
| 8 | `create_employee`, lines 79-83 | It checks for an existing code, then inserts. Two requests at the same moment can both pass the check. There is also no unique index to stop the second one. | Send the same `emp_code` ten times in parallel. | Unique index on `emp_code`. I insert straight away and turn `DuplicateKeyError` into a 409. |
| 9 | `EmployeeIn`, lines 53-60 | It accepts anything: a wrong `emp_code`, a bad email, impossible dates, bad shift times, an empty name, and a shift that starts and ends at the same time. | `shift_start: "25:99"` or `joined_on: "yesterday"` is stored and breaks calculations later. | Patterns and length limits from the contract, a real calendar-date check, and a start-not-equal-to-end check. |
| 10 | `create_employee`, lines 82 and 85 | `created_at` is a naive local datetime and goes out as ISO text. The contract wants epoch milliseconds. | `created_at` in the response is a string. | Stored as a UTC datetime and returned as milliseconds. |
| 11 | `list_employees`, line 93 | `skip = page * page_size` skips the whole first page. | `page=1&page_size=20` starts at the 21st employee. The first 20 can never be seen. | `skip = (page - 1) * page_size`. |
| 12 | `list_employees`, lines 91-95 | `total` counts every employee, not the filtered ones. There is no sort, so the order is not guaranteed. `if department:` also treats an empty string as "no filter". | `department=Ops&page_size=5` returns a total of all employees. | `count_documents` uses the same filter, results are sorted by `emp_code`, and the filter checks `is not None`. |
| 13 | `list_employees` and `list_attendance`, the `page` and `page_size` parameters | Nothing limits them. In `list_employees`, `page=0` gives a negative skip and a server error. In `list_attendance`, `page=0` quietly returns an empty list. A huge `page_size` returns everything. | `page=0`, or `page_size=100000`. | `page >= 1` and `1 <= page_size <= 100`, both return 422 otherwise. A skip past the total returns an empty page. |
| 14 | `punch_in`, lines 101 and 113 | There is no check for an unknown employee. `emp` is `None` and `emp["shift_start"]` raises `TypeError`, so the client gets a 500. | `emp_code: "NOPE"`. | Return 404. |
| 15 | `punch_in`, line 102 | `if body.punched_at` treats `0` as "not given". There is no range check, so epoch seconds are accepted as milliseconds, and a huge number can crash. | `punched_at: 1783312500` (seconds) is saved as a date in January 1970. | Strict integer between 100000000000 and 4102444800000. Floats, strings and booleans get 422. |
| 16 | `PunchInIn` and `punch_in`, lines 66 and 109 | `status` can be any string. | `status: "ABSENT"` or `"banana"` is stored. | Only `PRESENT`, `WFH` and `ON_DUTY` are accepted. |
| 17 | `punch_in`, line 103 | The date is just the local calendar date of the punch. The overnight rule is ignored. | An overnight employee punches in at 00:10 and the record gets the next day's date instead of the shift's day. | `attendance_date_for` applies the IST date and the overnight exception. |
| 18 | `punch_in`, lines 104-118 | Same check-then-insert problem as row 8, and no unique index. | Two identical punch-ins at the same moment both return 201. | Unique index on `(emp_code, date)`. A `DuplicateKeyError` becomes a 409. |
| 19 | `punch_in` line 119, `list_attendance` line 149 | The response contains an internal `id`, which the contract forbids. Datetimes go out as ISO strings instead of milliseconds. | The punch-in response has an `id` field. | `serialize_attendance` returns only the contract fields, with times in milliseconds. |
| 20 | `list_attendance`, lines 144-147 | It loads every matching record into memory, then sorts and slices in Python. It sorts by `date` only, so records on the same date have no fixed order. | 100,000 records and no filter: slow, and it uses a lot of memory. | Filter, sort (`date` descending, then `emp_code`), skip and limit all happen in MongoDB, with indexes behind them. |
| 21 | `list_attendance`, lines 127-129 and 134-143 | Dates and status are not validated, `date_from` after `date_to` is not rejected, and old records without `history` or `half_day` come out with those fields missing. | `date_from=garbage`, `status=BOGUS`, or `date_from=2026-07-31&date_to=2026-07-01`. | Validators, a 422 for a reversed range, and defaults for missing fields. |
| 22 | `health`, line 74 | It always says ok and never talks to MongoDB. | Stop the MongoDB container. `/health` still returns 200. | It pings MongoDB and returns 503 if there is no answer. |
| 23 | whole file | No indexes are created, so only the default `_id` index exists. Queries on `emp_code` and `date` scan the whole collection (Compass shows `COLLSCAN` for them). Database errors also come back as a 500. | Run explain in Compass on `{emp_code, date}` against the starter's collection. | Indexes are created at startup, and database errors return 503. |

## Things I looked at and decided were not defects

- `load_dotenv()` on line 20 does not override variables that are already set. That is what the contract asks for (real environment variables win over `.env`).
- The IST offset on line 25 (+05:30) is right.
- `/health` already returns the right body, `{"status": "ok"}`. Only the missing ping was wrong.
- `list_employees` leaves `_id` out with a projection, and `create_employee` pops it before returning. The idea is right, so I kept it in my serializers.
- The defaults written by `punch_in` (`punch_out` null, `overtime_minutes` 0, `half_day` false, `history` empty) match the contract.
- `status_code=201` on the two POST routes is correct.
